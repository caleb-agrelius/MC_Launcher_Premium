# Launching (Play)

Turning an installed modpack into a running Minecraft. Entry point: `PlayModpack()` in `src/Game/Launcher.{h,cpp}`, started by `PlayService::Start()` in `src/Services/Play/PlayService.cpp`.

## Where to click
- **My Library:** each pack card has a **PLAY** button, for packs from every source. While the pack is being prepared, the card shows the current step, a spinner, a progress bar when the size is known, and a **Cancel** button. Pressing Cancel immediately shows a disabled **Cancelling...** button and the step "Cancelling..." until the worker stops (downloads stop between chunks; a running loader installer is terminated). While the game runs it shows "Minecraft is running" and a **Stop game** button, which asks for confirmation and then force-closes Minecraft (unsaved progress since the last autosave is lost). Errors appear in red on the card.
- **Discover:** the big **PLAY** button works once the selected pack is in My Library. It starts the same play flow and switches to My Library. Otherwise it's disabled, with a hint to install the pack's files.
- A Microsoft account that owns Minecraft: Java Edition is required, and it's checked online before every launch (see [accounts.md](accounts.md#account-check-before-play)). There is no offline play. Pressing Play without an account, or when the check fails, shows an error on the card.

## Steps (`PlayModpack`)
`PlayModpack` has two front ends that share the remaining steps (`InstallAndLaunch`):
Play uses the pack's active installed version: its install folder (`PlayRequest::extractedDir`) and game folder (`instanceDir`), see [library.md](library.md#installed-versions).
- **`.mrpack` packs** (Modrinth and the local index): steps 1 and 2 below.
- **Whole-pack installs** (CurseForge, FTB, Technic, ATLauncher), recognized by a `pack.json` in the install folder (`IsWholePackInstall`). The install plan already filled the game folder, `<install folder>/minecraft/`, so steps 1 and 2 are replaced by `ReadInstalledPack()`:
  - It reads the Minecraft version, `loader` and `loaderVersion` from `pack.json`. `ParseLoaderName` maps `forge`, `neoforge`, `fabric` and `quilt` (any case). An unknown loader fails with a message naming it.
  - `NormalizeLoaderVersion` strips the forms sources wrap versions in: a `forge-`/`neoforge-`/`fabric-`/`quilt-` prefix, a leading `<mc>-` and a trailing `-<mc>`. `forge-47.2.0`, `1.20.1-47.2.0` and `47.2.0-1.20.1` all become `47.2.0`.
  - **No loader declared** (Technic single-zip packs): the loader is detected from `minecraft/bin/version.json`, else the `version.json` inside `minecraft/bin/modpack.jar`, by finding the loader's own library (`net.minecraftforge:forge`, `net.minecraftforge:minecraftforge`, `net.neoforged:neoforge` or `forge`, `net.fabricmc:fabric-loader`, `org.quiltmc:quilt-loader`), like Prism's `TechnicPackProcessor`. If none is found there, Forge's universal jar in `minecraft/jarmods/` is checked the same way (old ATLauncher packs list Forge as a `forge` jar mod). If none is found, the pack launches as vanilla.
  - **Old Forge from the pack's own jar:** when the loader was found in a jar (`InstalledPack::loaderJar`) and the Minecraft version is before 1.13 (`IsLegacyForgeMinecraft`), Forge is installed from that jar instead of its installer, because those installers can't run headless (`InstallForgeFromJar`, `src/Game/Loaders.cpp`):
    - The jar's `version.json` is written to `versions/<id>/<id>.json`, with `inheritsFrom` and `jar` set to the Minecraft version.
    - The Forge library is the jar itself, copied into `libraries/` (no download). Library URLs on the retired `files.minecraftforge.net` move to `maven.minecraftforge.net`, other `http://` URLs become `https://`, and libraries marked `clientreq: false` are dropped.
    - Forge for Minecraft 1.6, 1.7.2, and 1.7.10 builds before 10.13.2.1230 crashes on Java 8 while sorting its tweakers. For those, `LegacyJavaFixerJob` puts LegacyJavaFixer 1.0 (Forge's own fix, from its maven, SHA-1 checked) in the game folder's `mods/` (`NeedsLegacyJavaFixer`). Mojang has no older Java for these versions.
    - Checked live with ATLauncher's Survivalists' Nightmare (Minecraft 1.6.4, Forge 9.11.1.965 from its jar mod): Minecraft 1.6.4 started and FML loaded its 6 mods.
  - A missing game folder fails with "Install it again".

1. **Read the pack:** `ReadMrpackIndex()` (`src/Game/PackInstance.cpp`) reads `modrinth.index.json` from the install folder. It takes the Minecraft version and loader from `dependencies` (`fabric-loader`, `quilt-loader`, `neoforge`, `forge`) and the client files: entries with `env.client == "unsupported"` are skipped, and paths that are absolute or climb out of the instance are rejected.
2. **Prepare the instance:** `PrepareInstance()` downloads the listed files into the game folder. The first time each pack version is prepared, it copies `overrides/` then `client-overrides/` over it, using `\\?\` paths (`ExtendedPath`) so configs nested past 260 characters copy correctly. Downloads, size checks and SHA-1 checks also use long paths. The marker `.mclp-prepared` in the game folder records the version and every file it listed, so later launches keep the player's own option and config changes. When a new pack version is prepared, files the old version listed but the new one doesn't (mods the pack dropped) are deleted first. Files the player added were never listed, so they stay. A listed file with a `<name>.disabled` copy (turned off on the Manage page) isn't downloaded again. Pack files the player removed (`PlayRequest::contentChanges`, see [manage.md](manage.md#your-changes)) are dropped from the list first, and after preparing, `ApplyContentChanges` puts the player's changes back. **Repair files** (`RepairModpack`) does the same.
   Then, if any game options are turned on in Settings > Game options, `ApplyGameOptions()` writes them into the instance's `options.txt` ("Applying game options"; see [settings.md](settings.md)).
3. **Vanilla Minecraft:** `InstallVanillaJson()` gets `versions/<mc>/<mc>.json` from Mojang's version manifest, and `ResolveVersion()` reads it.
4. **Java:** if the launch settings name a Java (`launch.javaPath`, a detected Java or a custom path), it is used: on Windows a `java.exe` is swapped for the `javaw.exe` next to it, and a folder means its `bin/javaw.exe` (`bin/java` on Linux, `JavaExecutableName`). A path that doesn't exist fails with an error naming it. Otherwise (**Automatic**, like Prism Launcher):
   - `FindJavaInstalls()` (`src/Game/JavaFinder.{h,cpp}`) lists the Javas on this PC, and `PickJava()` takes the newest one whose major version equals the version JSON's `javaVersion.majorVersion` (default 8). Newer majors aren't used, since Minecraft and loaders often break on them. When versions tie, a Mojang runtime wins. The step shows "Using Java 17.0.8 (Eclipse Adoptium)".
   - With no match, `InstallJavaRuntime()` installs the Mojang Java runtime named by the version's `javaVersion.component` (default `jre-legacy`) into `minecraft/runtime/<component>/`. `.manifest-sha1` records the installed manifest, so later launches skip it, and a finished runtime counts as an installed Java from then on. If Mojang can't be reached, an already-installed runtime is used.
   - Where Javas are found on Windows: `JAVA_HOME`; `PATH` folders named `bin`; the registry keys of Oracle (`JavaSoft`), Eclipse Adoptium/Foundation, AdoptOpenJDK, Microsoft, Azul Zulu, BellSoft and Amazon Corretto (their `JavaHome` or `Path` values); `Program Files` and `%LOCALAPPDATA%\Programs` vendor folders; IntelliJ's `~/.jdks`; the official launcher's runtimes (`%APPDATA%\.minecraft\runtime` and the Microsoft Store copy); Prism's `%APPDATA%\PrismLauncher\java`; and `minecraft/runtime/` (only runtimes with `.manifest-sha1`, so half-downloaded ones are skipped). On Linux: `JAVA_HOME`; each `java` on `PATH`, followed through its links to the real home; `/usr/lib/jvm`, `/usr/lib64/jvm`, `/usr/java`, `/opt` and `/opt/java`; `~/.jdks`; SDKMAN's `~/.sdkman/candidates/java`; `~/.minecraft/runtime` (also the Flatpak copy); Prism's `java` folder (also as a Flatpak or Snap); and `minecraft/runtime/` as above.
   - Each home needs `bin/java.exe` (`bin/java` on Linux). Its version, vendor and architecture come from its `release` file (`JAVA_VERSION`, `IMPLEMENTOR`, `OS_ARCH`), else from its folder name (`jdk-17.0.2`, `jre1.8.0_381`, or a Mojang component such as `java-runtime-delta` = 21). 32-bit builds are skipped (Minecraft needs more memory than they allow). Each home is listed once, newest first. Javas in Mojang's component folders (ours, the official launcher's, and Prism's copies) are labeled "(Mojang)".
5. **Game files:** `InstallGameFiles()` downloads the client jar, libraries, old-style natives, the log4j config, the asset index and assets. Natives are extracted once into `versions/<id>/natives/`, with a `.extracted` marker. Pre-1.7.3 "virtual" asset indexes are also copied by name into `assets/virtual/<index>/`.
6. **Mod loader:** `InstallLoader()` (`src/Game/Loaders.cpp`):
   - **Fabric / Quilt:** fetches the loader's ready-made profile JSON from `meta.fabricmc.net` / `meta.quiltmc.org` into `versions/<id>/`, skipped if it already exists.
   - **Forge / NeoForge:** downloads the official installer into `minecraft/installers/` and reads the version id from `version.json` inside it. Unless that version and all its generated libraries already exist, it runs the installer headless (`--installClient <root>`, retried with `--install-client`) with the runtime's console `java.exe`. Output goes to `minecraft/logs/loader-installer.log`. A `launcher_profiles.json` stub is created because the installer requires it. NeoForge for 1.20.1 uses the old `net.neoforged:forge` artifact. Installers without `version.json` (very old Forge) fail with a clear error.
7. Resolve the loader's version and download its extra libraries.
8. **Jar mods:** classic jar mods (zips in the game folder's `jarmods/` without a `version.json`, i.e. Minecraft 1.5 and earlier) are patched into a copy of the game jar, `<game folder>/.mclp/patched-client.jar`, which then replaces the client jar on the classpath (`FindJarMods`, `BuildPatchedJar` in `src/Game/JarMods.cpp`):
   - The order is the one the pack's `pack.json` `files` lists them in, then any others by name. Later mods override earlier ones, and `META-INF/` is left out, since its signatures would no longer match.
   - The patched jar is rebuilt only when the game jar or a jar mod changes: their names, sizes and times are recorded in `patched-client.jar.inputs`.
   - Jars with a `version.json` are a loader (Forge 1.6 and later), not jar mods, and are installed as described above.
9. **Launch:** versions whose asset index sets `map_to_resources` (before 1.6) first get their assets copied by name into `<game folder>/resources/`, missing ones only. Then it builds the command line and runs `javaw.exe` (`java` on Linux) from the game folder, without a console. stdout/stderr are appended to `<game folder>/logs/launcher-output.log`. The worker waits until the game exits. A non-zero exit code is reported on the card.

## Version JSON handling (`src/Game/GameFiles.cpp`)
- `ResolveVersion()` follows `inheritsFrom` and merges from vanilla up. Children override `mainClass`, `type`, `minecraftArguments`, `assetIndex`, `javaVersion` and `logging`, and append to `arguments.jvm`/`arguments.game`. The client jar comes from the version that has `downloads.client` (or `jar`).
- Libraries are taken from the most specific version first and de-duplicated by `group:artifact[:classifier]`, so a loader's copy of a library wins.
- `RulesAllow()` evaluates `rules` for the running OS (Windows x64 or Linux x64; see [platforms.md](platforms.md)). Feature rules (demo, custom resolution, quick play) never match.
- Libraries with `downloads.artifact` use its URL and SHA-1. Libraries without it (Fabric/Quilt style) use `url` (default `libraries.minecraft.net`) plus the maven path. Libraries with an empty URL must already exist, because Forge's installer generates them.

## Downloads
`DownloadAll()` skips files that exist with the expected size and downloads the rest on 8 threads. Each file goes to a uniquely named `<file>.<tag>-<n>.part`, is checked against its SHA-1, then renamed into place. Two packs or two launcher windows fetching the same shared file therefore don't collide, and a file another downloader finished first counts as done. Replacing an existing file (e.g. a server's `server.jar` when its Minecraft version changes) is retried for about 2 seconds, removing the old file halfway, because Windows can keep a just-closed file locked briefly. Each file gets 3 download attempts, and the first failure stops the step. Progress is reported as "<step> (done/total)".

## Command line
- Placeholders (`${auth_player_name}`, `${classpath}`, `${natives_directory}`, `${library_directory}`, `${classpath_separator}`, ...) are substituted. Unknown ones become empty. `user_type` is `msa`.
- Launch settings come from Settings > Minecraft (`Settings::launch`, see [settings.md](settings.md)), copied into `PlayRequest::launch` when Play is pressed.
- JVM arguments, in order: `-Xms<minMemoryMb>M` (only when set), `-Xmx<maxMemoryMb>M` (default 4096), the version's `arguments.jvm` or, for old versions, `-Djava.library.path` and `-cp`, the log4j config argument when the version has one, then the player's own JVM arguments. Those are split on spaces, with double quotes grouping words (`SplitArguments`), and go last so they override the defaults.
- Game arguments: the version's, then `--fullscreen` when fullscreen is on, or `--width`/`--height` when a custom window size is set. The version JSON's own resolution arguments are behind a feature rule that never matches, so nothing is duplicated.
- **When the game starts** (`launch.afterLaunch`), on the "Playing" step: keep the launcher open (and show a "Minecraft started" toast), minimize it (restored when the game exits), or close it. Closing works like closing the window by hand: the game keeps running.
- A play that fails (not cancelled) also shows an error toast. An unexpected exception during preparation is caught and reported as "Unexpected error: ..." instead of ending the app.
- For Java 9 and newer, JVM arguments go in `.mclp-jvm-args.txt` in the game folder and are passed as `@file`, to stay under Windows' command-line limit. The main class and game arguments, including the access token, stay on the command line.

- Every launch also passes `-Dfml.ignoreInvalidMinecraftCertificates=true` and `-Dfml.ignorePatchDiscrepancies=true`, as Prism and MultiMC do. Old Forge checks Mojang's signature on the game jar, which current Java 8 rejects because the jar is SHA-1 signed, and then refuses to start. Versions that don't read these flags ignore them.

## Folders (gitignored, in the data folder)
- `minecraft/`: shared `versions/`, `libraries/`, `assets/`, `runtime/`, `installers/`, `logs/`, `launcher_profiles.json`, and `shared-files/` (see [shared-files.md](shared-files.md))
- `instances/<pack id>/` or `instances/<pack id>@<version>/`: `.mrpack` game folders (mods, config, saves, logs), one per installed version

## Limitations
- Windows x64 and Linux x64. The Linux path builds and passes the process checks in CI, but a pack hasn't been played on Linux yet (see [planned.md](planned.md#linux)).
- Mod files are kept by size, not re-hashed on every launch. **Manage > Repair files** in My Library re-checks them by hash.
- Classic jar mods for Minecraft 1.5 and earlier have unit checks, but haven't been tried with a real pack: ATLauncher's current pack list has none.
- Closing the launcher stops preparation but leaves a running game open. Only **Stop game** ends it from the launcher: it sets `PlayRequest::stopGame`, which makes `RunProcess` terminate the process (its `kill` flag) and `PlayModpack` return "Stopped". That shows a "Minecraft was closed" toast instead of an error.
